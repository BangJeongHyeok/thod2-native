# 플랫폼: 메인 루프·타이밍

- **상태:** 진행 중
- **관련 로드맵:** ROADMAP 1-3, 2-2
- **관련 코드:** `src/platform/` (예정), `src/core/patches/frame_wait.cpp`, `src/core/patches/frame_interp.cpp`, `src/core/patches/profiler.cpp` (개발용), `tools/compat/interp-test.ps1`
- **마지막 갱신:** 2026-10-28

## 주요 목표

모니터 주사율과 관계없이 게임 로직이 원본 속도로 돌게 한다. 최종적으로 메인 루프를 재구현해서 로직 업데이트(60Hz 고정 스텝으로 추정)와 렌더링을 분리한다. 이것이 고프레임 렌더 보간의 기반이다.

**완료 기준:** 60Hz, 144Hz, 240Hz 모니터와 vsync 켬/끔 모든 조합에서 게임 속도가 원본과 같다.

## 메인 루프 분석 결과 (2026-10-28)

Ghidra 디컴파일(전체 함수 덤프, 저장소 밖)로 확인했다.

```
RunApplication 0x4A5A10       콜백 5개 저장 (0x7DD124 = 틱 함수 RunTick)
└ RunMessageLoop 0x4A5920     PeekMessage 루프
   ├ 활성: [0x7DD124]() = RunTick 0x49DBD0
   └ 비활성: WaitFrameEnd (호출 0x4A59DF) + WaitMessage
RunTick 0x49DBD0
  1. 작업 대기열 5개 처리 (프레임을 건너뛰는 중이면 10개)
  2. UpdateGameFrame 0x40E850
     - SetupSceneProjection 0x418590 → BeginFrameScene 0x4AB320 (BeginScene, Clear, 배경색)
     - 입력 0x40E5F0 (UpdateInput, 조준)
     - 일시 정지 메뉴 0x40E620 또는 게임 모드 RunGameMode 0x460460 (모드별 함수. 여기서 태스크가 갱신과 그리기를 함께 한다)
     - 0x418620: 스프라이트 목록 0x41D000, EndFrameDraws 0x4AB350 (반투명 정렬 그리기, EndScene)
  3. 사격 번쩍임: 따로 BeginScene / DrawScreenFlash / EndScene
  4. EndTick 0x4AB2F0: WaitFrameEnd 0x4A4B30 (UpdateFrame = Flip, 그다음 16.67ms 대기), 콜백 [0x80ECCC], 0x4A6500
```

- **로직과 그리기가 한 함수 안에 섞여 있다.** 태스크가 자기 상태를 갱신하면서 바로 모델과 스프라이트를 그린다. 그래서 "로직만 한 번 더" 또는 "그리기만 한 번 더"를 부를 수 있는 함수 경계가 없다.
- **게임은 프레임 건너뛰기를 이미 가지고 있다.** WaitFrameEnd는 프레임이 `목표 + 보정`보다 늦으면 `g_frameSkipCount`(`0x7DCE2C`)에 `floor(경과 / (16.67 + 보정))`(최대 `[0x597438]` = 4)을 넣고 기다리지 않는다. 이 값이 0이 아닌 동안 BeginFrameScene, EndFrameDraws, 번쩍임이 빠지고 로직만 돈다. 그다음 프레임마다 1씩 줄인다. 다음 프레임 시간은 이전 프레임 끝에서 다시 잰다 (`g_lastFrameQpcLow`), 즉 4틱보다 오래 멈추면 그 시간은 따라잡지 않는다.
  - 이것으로 **게임 로직은 1틱 = 1/60초로 고정**이라는 것이 코드로 확인된다. 그리기를 빼도 로직은 그대로 돈다.
- **Direct3D 객체는 모두 D3DX 컨텍스트에서 온다** (`0x4A41C0`): `g_d3dxContext`(`0x7DCDE8`), `GetDD()` → `g_directDraw`(`0x7DCDEC`), `GetD3DDevice()` → `g_d3dDevice`(`0x7DCDF4`). 컨텍스트 메서드 위치(+0x4C UpdateFrame, +0x54 Clear, +0x58 SetClearColor, +0x44 RestoreSurfaces, +0x18 GetPrimary, +0x20 GetBackBuffer)는 DirectX 7 SDK `d3dxcore.h`의 `ID3DXContext` 순서와 맞는다.
- **장치 호출은 몇 종류뿐이다.** 게임 코드가 부르는 `IDirect3DDevice7` 메서드: BeginScene, EndScene, SetTransform, SetMaterial, SetLight, LightEnable, SetRenderState, SetTexture, SetTextureStageState, DrawPrimitive, ComputeSphereVisibility, EnumTextureFormats(초기화). 화면 지우기는 컨텍스트 Clear로 한다.
- **카메라는 모델 행렬에 합쳐져 있다.** VIEW 변환은 초기화 때 한 번(`0x4A6A60`) 고정값으로 넣고, 모델마다 DrawModel/DrawModelAlt가 `SetTransform(WORLD, 기록 + 0x34)`로 월드·카메라를 합친 행렬을 넣는다. 투영(PROJECTION)은 틱마다 SetMatrixMode가 넣는다.

## 틱 사이 보간 방식 (G4-2)

`[display] interpolate = 1` (`src/core/patches/frame_interp.cpp`):

1. EndTick의 `call WaitFrameEnd`(`0x4AB2F0`)를 우리 함수로 바꾼다. 처음 불릴 때 장치와 D3DX 컨텍스트의 함수 표에 훅을 건다 (그 틱은 원래 WaitFrameEnd).
2. **기록:** 그다음부터 한 틱 동안의 장치 호출을 목록으로 모은다. 상태 변경(변환, 렌더 상태, 텍스처, 재질, 조명)은 장치에도 그대로 보내서 게임의 ComputeSphereVisibility가 맞게 동작하게 한다. BeginScene/EndScene, DrawPrimitive, 컨텍스트 Clear는 실행하지 않고 기록만 한다. 정점은 복사하고, 텍스처는 AddRef해서 목록이 버려질 때까지 잡아 둔다.
3. **짝 맞추기:** 틱이 끝나면 이번 틱의 행렬마다 이전 틱의 같은 행렬을 찾는다. 열쇠는 (변환 종류, 모델 포인터, 그 모델이 이번 틱에 몇 번째로 그려졌는지). 모델 포인터는 SetTransform의 호출 위치가 DrawModel/DrawModelAlt 안이면 `행렬 주소 - 0x34 + 0xC`에서 읽는다.
4. **재생:** 다음 틱 시각까지 반복해서, 지금 시각이 틱 사이 어디인지(`t`)에 따라 이전 틱 → 이번 틱 행렬을 원소별로 섞어서 목록을 다시 실행하고 UpdateFrame으로 보낸다. Flip이 수직 동기화를 기다리므로 모니터 주사율만큼 그려진다.
   - 한 틱에 `interp_snap`(기본 2.0) + 거리의 1/4보다 많이 움직였거나, 회전 축이 약 25도보다 많이 돌았거나, 크기가 25%보다 많이 바뀐 행렬은 섞지 않고 이번 틱 값을 쓴다 (화면 전환, 짝이 틀린 경우).
   - 작업 대기열(로딩)에 일이 있으면 남은 시간을 먼저 거기에 쓰고, 그 틱은 끝에 한 번만 그린다. 원래 WaitFrameEnd가 남는 시간을 전부 로딩에 쓰기 때문이다 (아래 측정).
   - 1틱보다 늦으면 다음 틱을 그리지 않고 로직만 돌린다 (`g_frameSkipCount = 1`). 8틱보다 늦으면 원래처럼 4틱만 따라잡고 시계를 다시 맞춘다.
5. 화면은 보간 때문에 1틱 늦게 따라간다 (이번 틱 상태가 다 보이는 것은 다음 틱이 시작될 때).

보간하지 않는 것: 2D(XYZRHW 사각형, 조준점·HUD·자막), 조명 방향, 정점 데이터 자체(모델 모양이 바뀌는 효과).

`[debug] profile = 1`로 메인 스레드를 약 1ms마다 샘플링했다. 테스트 사본, dgVoodoo2 권장 설정, 타이틀·데모 화면.

### 측정

| 항목 | 값 (5초 구간 5개) |
|---|---|
| 메인 스레드 CPU | 87~99% (사용자 모드 64~89%, 커널 9~23%) |
| 다른 스레드 CPU | 각 3% 이하 |
| 샘플 위치: `ntdll.dll` | 52~55%. 대부분 `RtlQueryPerformanceCounter` 내부 (`ntdll+0x62F0E`, 함수 시작 `+0x62E50`) |
| 샘플 위치: `Hod2.exe` | 34~43%. 대부분 `0x4A4D0F`~`0x4A4D63` 구간과 `0x49E0C0`~`0x49E0D6` |
| 샘플 위치: 그래픽 관련 (`D3DImm`, `D3D11`, 드라이버, `DDRAW`) | 합계 약 4~5% |

### 원인: 프레임 끝에서 바쁜 대기

`0x4A4B30` 함수(호출하는 곳: `0x4A59DF`, `0x4AB2F0`)가 프레임마다 목표 시간이 될 때까지 기다린다. 바이트를 직접 해석한 결과:

```
목표(ms) = [0x597444] (16.6667 = 1000/60) + 보정값 [0x7DCE30] (±10ms 범위, 0.2씩 조정)
loop (0x4A4D0F ~ 0x4A4D63):
    if [0x7DCDFC] != 0: call [0x7DCDFC](남은 ms)      ; 콜백
    QueryPerformanceCounter(&now)                      ; 호출 직후 주소 0x4A4D30
    경과(ms) = (now - [0x7DCE38]) * 1000.0 / [0x7DCE3C](주파수)
while 경과 < 목표
[0x7DCE38] = now
```

- **잠들지 않고 시간을 계속 읽으며 돈다.** 이것이 CPU 100%의 원인이다.
- 목표가 고정 16.67ms이므로 **게임은 모니터 주사율이 아니라 이 타이머로 60fps에 맞춰진다.** 고주사율 모니터에서 `Flip(WAIT)`이 빨리 끝나도 여기서 60fps로 맞춰질 가능성이 높다 (G3에서 확인).
- 근처 데이터: `[0x59744C]` = 60, `[0x597440]` = 10.0(보정 상한 ms), `[0x59743C]` = 0.2(보정 단계), `[0x597450]` = 20, `[0x597454]` = 333 (보정 판단 주기 ms로 추정).

### 대기 중 콜백

- 콜백 칸 `[0x7DCDFC]`에는 `0x49DF0B`의 `mov dword [0x7DCDFC], 0x49E0C0` 명령이 `0x49E0C0`을 저장한다 (즉시값은 `0x49DF11`~`0x49DF14`).
- `0x49E0C0(남은 ms)`: 남은 시간이 1.0ms보다 크면 `0x41D5D0`으로 넘어간다.
- `0x41D5D0` → `0x41D620`: **작업 대기열에서 하나를 꺼내 처리**한다. 64칸 순환 대기열(항목 16바이트, `0x7D8EB0`), 읽기 위치 `[0x7D8AA8]`, 쓰기 위치 `[0x7D8AAC]`. 처리 함수는 `0x41D670`이 `0x587C30` 함수 표에서 골라 부른다.
- 즉 프레임 사이 남는 시간에 쌓인 작업을 하나씩 처리한다. 대기열이 비어 있으면 시간 측정만 반복한다.

### 수정 방향 (G2)

- `0x49DF11`의 즉시값 `0x49E0C0`을 우리 콜백 주소로 바꾼다 (코드 4바이트, 바꾸기 전에 원래 값 확인).
- 우리 콜백: 원래 콜백(`0x49E0C0`)을 부른 뒤, **대기열이 비어 있고** 남은 시간이 여유분(약 1ms)보다 크면 `CreateWaitableTimerExW(HIGH_RESOLUTION)`로 `남은 시간 - 여유분`만큼 잠든다. 대기열에 일이 있으면 바로 돌아가서 원래처럼 처리한다.
- 시스템 타이머 정밀도(`timeBeginPeriod`)는 바꾸지 않는다.

## 바쁜 대기 → 잠자기 수정 결과 (2026-10-15)

`[timing] frame_wait_sleep` 패치 (`src/core/patches/frame_wait.cpp`). `tools/compat/frame-wait-compare.ps1`로 같은 조건(테스트 사본, dgVoodoo2 권장 설정, 타이틀·데모, 22초 중 앞 6초 제외)에서 비교했다. 프로파일러와 DirectDraw 기록을 켠 상태라 그 부하(약 1~2%)가 포함되어 있다.

| 설정 | 프로세스 CPU | 메인 스레드 CPU (5초 구간) | 초당 Flip | 평균 프레임 간격 | 간격 표준편차 (5초 구간) |
|---|---|---|---|---|---|
| 끔 (원본 동작) | **102%** | 93~98% | 59.0~60.4 | 16.64~16.92 ms | 0.4~4.5 ms (안정 구간 1.0~1.5) |
| **켬, 여유 1.0ms (기본값)** | **25%** | **13~18%** | 59.8~60.2 | 16.64~16.72 ms | 1.4~2.4 ms |
| 켬, 여유 2.0ms | 29% | 18~25% | — | 16.64~16.72 ms | 1.1~2.2 ms |
| 켬, 여유 3.0ms | 30% | 22~27% | — | 16.65~16.70 ms | 1.1~1.8 ms |

- CPU는 약 4분의 1로 줄었고, 프레임 속도와 평균 간격(16.67ms)은 그대로다.
- 간격 흔들림은 켰을 때 조금 커 보이지만, 여유를 늘려도 실행마다의 차이 수준에서 뚜렷하게 줄지 않았다. 흔들림의 주원인은 수직 동기화·화면 합성(DWM)과 `Flip(WAIT)`의 상호작용으로 보인다. 그래서 기본 여유는 1.0ms로 둔다.
- 간격 통계는 `ddraw_trace`가 primary `Flip` 사이 시간을 재서 5초마다 기록한다 (`frame interval over N frames: avg/min/max/stddev`).

## 고주사율 확인 결과 (2026-10-15)

**주 모니터(DISPLAY2)는 2026-10-15 0시 무렵 사용자가 239.76Hz로 바꿨다** (그 전, 2026-10-14 조사 때는 60Hz). 처음에는 이것을 모르고 "60Hz 모니터에서 흉내 낸다"는 전제로 시험했다. 이후 시험 스크립트가 측정 중 모니터 모드를 기록하도록 고쳐서 다시 측정했다.

개발용 설정 `[debug] flip_override`로 primary `Flip`의 플래그를 바꿀 수 있다 (`tools/compat/refresh-test.ps1`).

- `1` = `DDFLIP_NOVSYNC` 추가: `Flip`이 수직 동기화를 기다리지 않는다. **주사율이 무한히 높은 모니터**와 같은 조건.
- `2` = `DDFLIP_INTERVAL2` 추가: 수직 동기화 2번에 한 번.
- 게임 속도는 타이틀 카메라(`cam\cp_title.bin`)를 읽은 뒤 데모 카메라(`cam\cp_tuto.bin`)를 읽기까지의 시간으로 쟀다.
- `frame_wait_sleep`(기본 켬)이 적용된 상태.

### 실제 240Hz 모니터 측정 (모니터 모드 기록 포함)

| 환경 | 측정 중 주 모니터 모드 | flip_override | 초당 Flip | 타이틀 → 데모 |
|---|---|---|---|---|
| dgVoodoo2 권장 설정 (테두리 없는 창) | 1920×1080 **240Hz** | 0 | 59.6~60.4 | 8.03 s |
| dgVoodoo2 권장 설정 | 1920×1080 **240Hz** | 1 | 59.6~60.2 | 8.03 s |
| Windows 기본 DirectDraw (전체 화면 독점) | 게임이 바꾼 640×480 **240Hz** | 0 | 59.4~60.0 | 7.97 s |
| Windows 기본 DirectDraw | 640×480 **240Hz** | 1 | 59.4~59.8 | 7.98 s |

- 게임이 `SetDisplayMode(640, 480, 16, refresh 0)`으로 화면 모드를 바꿀 때 주사율은 240Hz로 잡혔다. 이 상태에서도 60fps다.

### 그 전 측정 (모니터 모드 기록 없음, 240Hz였을 가능성이 높음)

| 환경 | flip_override | 초당 Flip | 타이틀 → 데모 |
|---|---|---|---|
| dgVoodoo2 권장 설정 | 0 (원래대로) | 59.8~60.2 | 8.03 s (2회) |
| dgVoodoo2 권장 설정 | **1 (수직 동기화 끔)** | 59.8~60.4 | **8.03 s (2회)** |
| dgVoodoo2 권장 설정 | 2 (30Hz) | 59.8~60.2 | 8.03 s |
| Windows 기본 DirectDraw | 0 | 59.2~59.8 | 8.00 s |
| Windows 기본 DirectDraw | **1** | 59.4~59.8 | **8.03 s** |
| Windows 기본 DirectDraw | 2 | 59.8 | 7.97 s |

결론:
- **240Hz 모니터에서도, 수직 동기화를 꺼도 초당 60프레임, 게임 속도 그대로다.** 프레임 속도와 게임 속도를 정하는 것은 `Flip`이 아니라 `0x4A4B30`의 고정 16.67ms 타이머다. → **고주사율 모니터에서 게임이 빨라지지 않는다.**
- 2026-10-15 0시 무렵부터의 다른 측정(`frame_wait_sleep` 비교 등)도 240Hz 상태였을 수 있다. 그 결과(초당 60프레임, 평균 간격 16.67ms)는 이 결론과 맞는다.
- `DDFLIP_INTERVAL2`는 dgVoodoo2와 Windows 기본 DirectDraw(호환 모드 포함) 둘 다에서 무시되었다 (여전히 60fps). 그래서 60Hz보다 느린 화면에서의 동작, 즉 게임 로직이 프레임 수에 묶여 있는지는 이 방법으로 확인하지 못했다.
- **주의:** 시험 중에 다른 창을 만지면 게임 창이 포커스를 잃어 게임이 멈추고, 타이틀 → 데모 시간이 늘어난다. 처음 시험에서 11.76 s, 13.33 s가 나온 것이 이 때문이었다 (사용자가 PC를 쓰던 중). 시험할 때는 PC를 건드리지 않는다.

### 2026-10-14 — 화면 모드 분석에서 넘어온 내용

- **결과:** 게임은 매 프레임 primary 버퍼에 `Flip(NULL, DDFLIP_WAIT)`를 부른다 (호출 위치 `0x4B9896`). 60Hz 모니터에서 **초당 59.7~59.8회**로, 프레임 속도가 수직 동기화(vsync)에 묶여 있다. 이 상태에서도 CPU 코어 1개를 100% 쓴다.
  - **가설:** 게임 속도가 프레임 수에 묶여 있다면, 120Hz 이상 모니터에서 `Flip`이 더 자주 끝나서 게임이 빨라질 수 있다. 고주사율 환경에서 확인 필요 (G1-5, compat-survey).
  - 갱신 (CPU 분석): 프레임 속도는 `Flip`이 아니라 `0x4A4B30`의 고정 16.67ms 타이머가 정하는 것으로 보인다. 가설은 G3에서 다시 확인한다.
- **상세:** [platform-display.md](platform-display.md) "화면 모드 분석 결과"

### 2026-10-14 — 호환성 조사에서 넘어온 내용

- **결과:** 실행 중 CPU 코어 1개를 100% 사용하고, 최소화하면 1%로 떨어진다. 대기 없이 도는 루프로 추정된다. 임포트에 `QueryPerformanceCounter`, `QueryPerformanceFrequency`, `GetTickCount`, `MsgWaitForMultipleObjects`가 있다. 고주사율 모니터에서 속도는 아직 확인하지 못했다 (테스트 PC가 60Hz).
- **상세:** [compat-survey.md](compat-survey.md), [reverse-engineering.md](reverse-engineering.md)
