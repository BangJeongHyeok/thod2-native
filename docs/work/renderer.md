## 주요 목표

DX7(DirectDraw7 + Direct3D7)을 쓰지 않는 자체 렌더러를 만든다. DX7 API 수준이 아니라 게임의 그리기 함수 수준에서 가로채서 렌더 인터페이스로 넘기고, 백엔드는 인터페이스 뒤에 둔다 (1차: D3D11). 이 결과로 임의 해상도, 와이드스크린, 안티에일리어싱, 고프레임 보간 렌더링을 지원한다. 초기 호환성 확보용으로 기존 래퍼를 임시로 쓸 수 있다.

**완료 기준:** 원본이 DX7을 전혀 쓰지 않고, 원본과 같은 화면이 나오며, 해상도와 화면 비율을 자유롭게 설정할 수 있다.

## 화면 비율 분석 (2026-10-15)

근거는 Ghidra 디컴파일, 바이트 해석, 실행 실험이다. 함수·전역 변수·코드 위치는 `re/`의 `doc = renderer.md` 행에 있다.

### 투영

- `SetupSceneProjection`(`0x418590`)과 `SetupProjectionNear`(`0x419590`)가 투영 행렬을 만든다: 단위 행렬 → `TranslateMatrix(g_projectionOffset)` → **`SetPerspective(0x1D3B, 4/3, near, 8000)`** → `SetMatrixMode(1)`이 `SetTransform(PROJECTION)`으로 장치에 넘긴다.
- `SetPerspective`(`0x4AB160`): `m11 = cot(반시야각)`, `m00 = m11 / 화면비`. 시야각 `0x1D3B`(65536분의 1바퀴 단위) = **세로 41.1°**. 4:3의 가로는 약 53.1°다.
- 4/3 값은 `push 0x3FAAAAAB` 명령의 즉시값 두 곳(`0x4185D4`, `0x4195C2`)뿐이다. 실행 파일 전체에서 `AB AA AA 3F`는 이 두 곳에만 있다.
- `SetupSceneProjection`은 `g_focalLengthPx`(`0x9A0FF0`) = 240 / tan(20.55°) ≈ **640**도 계산한다. 소프트웨어로 3D→화면 좌표를 구할 때 쓰는 초점 거리(640×480 픽셀 단위)다.

### 2D/HUD 그리기

- 그리기는 `DrawPrimitive` 래퍼 세 개뿐이다: `DrawStrip3D`(`0x4A4DE0`), `DrawList3D`(`0x4A4E60`)는 3D 정점(FVF `0x112`), **`DrawStripScreen`(`0x4A4E20`)은 화면 좌표 정점(XYZRHW, FVF `0x1C4`)**.
- `DrawStripScreen`을 부르는 곳은 `DrawScreenQuad`(`0x4A6ED0`)와 화면 번쩍임 `DrawScreenFlash`(`0x49DAB0`, 0..639×0..479 전체 사각형) 두 곳이다.
- **모든 2D 요소는 `DrawScreenQuad`를 지난다.** 스프라이트 레코드(15 dword: `+7` x, `+8` y, `+9`/`+10` 크기, `+5` 회전, `+3` 텍스처)를 받아 회전·크기를 적용한 사각형을 그리고, 깊이는 투영 행렬(`g_projectionMatrix` m22, m32)로 계산한다.
- 경로: 게임 코드 → `DrawSprite2D`(`0x41C700`, 24곳에서 호출: HUD, 메뉴, 조준점, 타이틀) → `SubmitSprite`(`0x4AC140`) → `SubmitScreenQuad`(`0x4A6E60`) → 불투명이면 바로 `DrawScreenQuad`(호출 위치 `0x4A6EBE`), 반투명이면 정렬 큐에 넣었다가 `FlushSortedDraws`(`0x4A7D00`)가 그림(호출 위치 `0x4A7DF9`).
- 3D 위치에 붙는 스프라이트도 화면 좌표로 바뀐 뒤 같은 경로를 탄다 (`0x480FB0`이 `g_focalLengthPx`와 화면 중심 320, 240으로 투영하는 예).
- 뷰포트는 정적 링크된 D3DX의 `CD3duContext::SetViewport`(`0x4BA870`)가 640×480 전체로 잡는다. 게임 코드에서 따로 바꾸는 곳은 찾지 못했다.

### 조준 변환

1. `UpdateShots`(`0x40CE90`): 사격 플래그와 쏜 위치(입력 모듈의 `TakeShotFlags`, `GetShotPosition`)를 플레이어별 `g_shotInput`(`0x9C6A80`)에 둔다. 화면 밖이면 (0xFFFF, 0xFFFF).
2. `UpdateAim`(`0x40CBD0`, `0x40E5F0`에서 입력 갱신 다음에 호출): 화면 좌표를 보정 표(`MapAimAxis` `0x40D400`)로 **화면 중심 기준 좌표**로 바꾸고 **가로 −320~319, 세로 −240~239로 자른다**. 결과는 `g_aim`(`0x9C7240`, 플레이어당 0x28바이트).
3. 키보드·조이스틱 조준은 `MoveAimDigital`(`0x40D000`)이 움직이고 ±320 / ±240으로 자른다.
4. **명중 판정은 화면 좌표가 아니라 3D 광선으로 한다.** `BuildShotRay`(`0x406130`)가 (aim_x, aim_y, −`g_focalLengthPx`)를 카메라 행렬로 돌려 월드 광선을 만든다.
5. 조준점은 `DrawCrosshair`(`0x4863C0`)가 (aim_x + 320, 240 − aim_y)에 `DrawSprite2D`로 그린다.

### 4:3 가로 범위가 박힌 곳

`g_focalLengthPx`를 쓰는 함수는 약 30개다. 대부분은 단순 투영(화면 좌표 = 320 + f·X/Z)이라 아래 "가상 4:3 좌표" 방식에서는 고칠 필요가 없다. 가로 범위(320, f×0.5)가 들어간 곳만 고쳐야 한다:

| 함수 | 내용 |
|---|---|
| `0x406330` | atan(320/f), atan(240/f): 4:3 반시야각 (컬링용으로 추정) |
| `IsInScreenRect` `0x409C30` | \|x\| ≤ f×0.5(=320), −240 ≤ y ≤ 240 |
| `0x445530`, `0x45C620` | 물체의 화면 상자가 ±320 안에 걸치는지 |
| `0x44C760` | 화면 가장자리(320)를 카메라 공간으로 되돌림 |
| `UpdateAim` `0x40CBD0` | 조준 −320~319 자르기 (`push 0xFFFFFEC0`, `push 0x13F`) |
| `MoveAimDigital` `0x40D000` | 조준 ±320 자르기 (상수 `0x4C39CC`, `0x4D0D10`, 즉시값 `0x43A00000`) |

상수 320.0(`0x4C39CC`), −320.0(`0x4D0D10`), 0.5(`0x4C33AC`)는 다른 곳에서도 같이 쓰므로 상수 자체를 바꾸면 안 되고, 위치별로 고쳐야 한다.

### 실행 실험 (`[debug] aspect_experiment`)

640×480 화면을 그대로 두고 dgVoodoo2가 16:9 화면 전체로 늘리게(`ScalingMode = stretched`) 한 뒤, 게임 쪽에서 맞춘다 (아나모픽 방식, Hor+: 세로 시야각 유지, 가로 확장).

- 단계 1: 4/3 즉시값 두 곳을 16/9로 바꾼다 (`PatchUint32`).
- 단계 2: 단계 1 + `DrawScreenQuad` 호출 두 곳을 바꿔서, 2D 사각형의 x를 화면 중심(320) 쪽으로 3/4배 하고 가로 크기도 3/4배 한다.

`tools/compat/aspect-capture.ps1`로 타이틀 카메라를 읽은 뒤 1.5초, 9.5초, 20초에 화면을 찍었다 (주 모니터 `\\.\DISPLAY2` 1920×1080, 찍을 때 60Hz로 읽힘). 이미지는 저장소 밖 `E:\Repos\hod2-native\screenshots\aspect\`.

| 변형 | 3D | 2D (HUD, 로고, 안내 상자) |
|---|---|---|
| `base` (지금 권장 구성) | 4:3, 양옆 검은 띠 | 정상 |
| `stretch` (늘리기만) | 가로로 늘어남 | 가로로 늘어남 |
| `proj` (단계 1) | **비율 정상, 양옆이 더 보임** | 가로로 늘어남 |
| `proj_2d` (단계 2) | **비율 정상, 양옆이 더 보임** | **비율 정상**. 가운데 4:3 영역에 모임 |

- **수치 확인 (`tools/compat/aspect-scalefit.ps1`):** Hor+가 맞다면 16:9 화면의 가운데 1440×1080은 4:3 원본 화면(`base`, 1440×1080)과 같아야 한다. 원본의 x를 화면 중심 기준으로 s배 해서 각 변형과 가장 잘 맞는 s를 찾았다 (밝기 차이 평균, 0–255).

  | 시점 | `stretch` | `proj` | `proj_2d` | `proj_2d`의 s=1.00 차이 |
  |---|---|---|---|---|
  | 1.5초 (타이틀) | 1.33 | 1.33 (큰 2D 로고가 늘어남) | **1.00** | 12.6 (s=1.33이면 46.6) |
  | 9.5초 (데모) | 1.33 | 1.00 | **1.00** | 2.8 |
  | 20초 (데모, 안내 상자) | 1.33 | 1.00 | **1.00** | **0.1** |

  HUD 줄(y 750–1050)만 보면 `proj_2d`는 세 시점 모두 s=1.00(차이 17.9, 3.3, 0.2), `proj`는 HUD가 늘어나서 차이가 크다(35.3, 19.3, 4.1). `stretch`가 항상 1.33으로 나오므로 측정 방법은 늘어남을 제대로 잡는다. **`proj_2d`는 원본과 같은 비율이고, 원본 4:3 화면에 양옆 240픽셀씩이 더해진 모습이다.** 타이틀 시점의 남은 차이는 같은 시각에 찍어도 애니메이션이 조금 다른 프레임이라서로 보인다 (확인 안 함).
- 데모 장면 양쪽 끝까지 배경이 그려졌고, 이 장면들에서는 가시 범위 판정 때문에 빠진 물체가 보이지 않았다. 다른 장면·적이 많은 장면은 아직 확인하지 않았다.
- 화면 번쩍임은 `DrawScreenQuad`를 거치지 않아서 계속 화면 전체를 덮는다 (의도대로).
- 조준과 HUD 배치는 아래 "조준", "HUD 배치"에서 맞췄다.

### 영화 화면 띠 (2026-10-15)

1챕터 시작 같은 영상 구간에서 게임이 위아래에 검은 띠를 넣는다. 투영만 16:9로 바꾸면 이 띠가 가운데(출력 약 220~1700픽셀)만 덮고 넓어진 양옆은 비어 있다 (사용자 발견).

- **띠는 2D가 아니라 카메라 공간의 3D 모델이다.** `UpdateLetterbox`(`0x413A40`, 작업 함수)가 단위 행렬에서 (0, ±0.35, −1)로 옮긴 뒤 모델 표(`g_modelTable` `0x9A4920`) 항목 **`0x93E`** 를 위·아래에 한 번씩 그린다 (`DrawModelByIndex` `0x418630` → `DrawModelPointer` `0x4A96D0` → `SubmitModel` `0x4A7270` → `DrawModel` `0x4A7310`).
- 시점 행렬은 상수 diag(1, 1, −1)(`g_viewMatrix` `0x5977C8`)이라 모델 행렬이 곧 카메라 공간 행렬이다. 띠 모델은 4:3 시야 폭보다 약 3% 넓게 만들어져 있다.
- 상태값 `g_letterboxState`(`0x9C8374`): 0 바로 표시, 1 40프레임 동안 들어옴, 3 나감, 4 유지, 5 표시 후 영상 모드 해제, 6 숨김, 8 띠를 세로 8배로 키워 화면 전체를 덮음. 영상 모드 동안 `g_cinemaMode`(`0x9C7080`) = 1이고, 사격 처리 코드가 이 값을 읽는다.
- **해결 (실험 단계 1 이상):** `DrawModel`·`DrawModelAlt` 호출 4곳(`0x4A72AF`, `0x4A7DEE`, `0x4A77EF`, `0x4A7DE4`)을 바꿔서, 모델이 `0x93E` 항목일 때만 행렬 x축을 16:9 ÷ 4:3 = 4/3배 한 뒤 그린다. 1챕터 시작 영상에서 위아래 띠가 1920픽셀 전체를 덮는 것을 화면으로 확인했다.
- **찾은 방법:**
  1. `[debug] trace_screen_quads`로 화면 가장자리에 걸친 2D 사각형을 기록했지만 띠에 해당하는 것이 없었다.
  2. 투영만 바꾼 단계(2D 압축 없음)에서도 띠 폭이 그대로라서 3D로 판단했다.
  3. 모든 모델의 행렬을 기록해 보니 회전 없는 단위 행렬, 위치 (0, 0.35, −1)인 모델이 하나 있었다. 실행 파일 데이터 영역의 고정 모델로, 실행 때 주소는 `0x894D20`이었다.
  4. 이 모델을 그릴 때 스택에 있는 복귀 주소를 기록해서 `0x413A40` → `0x418630` → `0x4A96D0`를 찾았다.
- **실패한 시도:** 처음에는 텍스처 `0xDA4`~`0xDEE`(640×480 그림을 128×32 조각 75개로 그림, `0x495ED0`)를 띠로 잘못 짚었다. 그 조각들을 압축에서 빼도 띠가 그대로여서 아니라는 것을 확인했다. 이 그림이 어느 화면인지는 아직 모른다. 또 처음 모델 추적은 `m22 > 0`만 봤는데, 시점 행렬이 z를 뒤집어서 조건이 틀렸다. 게다가 촬영 스크립트가 출력 줄을 걸러서 결과가 안 보였다.

### 조준 (2026-10-15)

**원래 있던 문제: dgVoodoo2 창에서 조준이 맞지 않는다.** 게임은 커서를 창의 클라이언트 픽셀 그대로(`GetCursorPos` − `ClientToScreen`, `GetCursorClientPos` `0x41E670`) 640×480 좌표로 쓴다. 원본의 640×480 전체 화면에서는 맞지만, dgVoodoo2 권장 구성(창이 1920×1080)에서는 **화면 왼쪽 위 640×480 픽셀만 게임 화면으로 해석된다.** 메모리를 읽어 확인했다 (4:3 권장 구성, 커서 화면 (240, 540) → 게임 커서 (240, 540) → 조준 x −79, 화면 가운데 (960, 540) → 화면 밖으로 처리되어 조준 0).

해결 (`[input] map_cursor`, 기본 켬, `patches/cursor_map.cpp`):

- `GetCursorClientPos` 호출 2곳(`0x41E4DA` 매 프레임, `0x41E928` 초기화)을 바꿔서, 원본 결과(클라이언트 픽셀)를 dgVoodoo2가 그리는 영역 기준 640×480 좌표로 바꾼다. 영역은 게임 폴더의 `dgVoodoo.conf` `ScalingMode`로 정한다: `stretched`면 창 전체, 그 밖에는 가운데 4:3 영역.
- 와이드스크린 실험(단계 1 이상)이면 이 값을 다시 넓은 가상 좌표로 바꾼다: x = 320 + (x − 320) × 4/3 (−107~747).
- 재구현 입력 갱신(`reimplement_update`)도 같은 변환을 쓴다 (`InputHost::MapCursor`). 비교 모드에서 원본 경로와 재구현 경로가 1,800프레임 모두 일치했다.

와이드스크린에서 조준이 넓은 좌표를 받게 고친 곳 (실험 단계 1 이상):

- `UpdateAim`의 x 범위 즉시값(`0x40CCD3`, `0x40CD67` = 319 → 426, `0x40CCD8`, `0x40CD75` = −320 → −427). **`MapAimAxis`(`0x40D400`)는 범위 밖이면 0을 돌려주고 무효로 표시한다** (Ghidra 디컴파일은 값을 그대로 돌려주는 것처럼 잘못 보여서, 어셈블리로 확인함).
- `UpdateAim`이 원시 x를 부호 없이 읽는 두 곳(`0x40CCC8`, `0x40CD6B`: `xor eax,eax; mov ax,[…]`)을 `movsx`로 바꾼다. 4:3 영역 왼쪽의 음수 x가 65536 − x가 되어 범위 밖 처리되던 문제다.
- `MoveAimDigital`(키보드·조이스틱 조준)의 ±320 비교·고정값과, 가로 범위 판정 함수들의 320.0 / −320.0 / 0.5 피연산자를 넓힌 값(±426.67, 0.6667)을 가리키게 바꾼다 (`re/locations.csv`의 `renderer.md` 행).

확인 (게임플레이 중 커서를 7곳에 놓고 메모리와 화면을 비교, `[debug]` 실험 단계 2 + `ScalingMode = stretched`):

| 커서 (화면) | 게임 커서 | 조준 (x, y) | 조준점 |
|---|---|---|---|
| (80, 400) 왼쪽 끝 | (−71, 178) | (−389, 62) | 커서 위치 |
| (240, 540) | (0, 240) | (−318, 0) | 커서 위치 |
| (960, 540) 가운데 | (320, 240) | (0, 0) | 커서 위치 |
| (1680, 540) | (640, 240) | (318, 0) | 커서 위치 |
| (1840, 400) 오른쪽 끝 | (711, 178) | (389, 62) | 커서 위치 |
| (960, 100), (960, 980) | (320, 44), (320, 436) | (0, 198), (0, −198) | 커서 위치 |

4:3 권장 구성(실험 끔, `stretched_ar`)에서도 커서 240 → 조준 −318, 1680 → +318이고 조준점이 커서 위치에 그려진다. 검은 띠 위(80, 1840)는 화면 밖으로 처리된다.

명중 판정은 조준 좌표와 초점 거리로 만든 광선(`BuildShotRay`)을 쓰고, 조준점도 같은 좌표에서 그려지므로 수학적으로 일치한다. 넓어진 양옆의 적을 실제로 맞히는지는 사람이 플레이해서 확인해야 한다.

### HUD 배치 (2026-10-15)

- 2D 그리기 함수 `DrawSprite2D`(`0x41C700`)와 `DrawSpriteAt`(`0x41C7A0`)를 부르는 곳은 46 + 197곳이다 (`DrawSpriteAt` 안의 1곳 제외). 목록은 `src/core/patches/hud_call_sites.h`이고, `tools/re/find_calls.py`로 만든다.
- 실험 패치가 이 호출을 모두 우리 함수로 지나가게 하고, `[debug] trace_screen_quads`로 호출 위치별 스프라이트와 좌표를 기록했다 (1챕터 영상과 게임플레이 약 70초, 22곳이 쓰임).
- **같은 호출 위치가 1P(왼쪽)와 2P(오른쪽) 요소를 함께 그린다** (예: `0x406940`이 스프라이트 `0x22E`를 x 82와 424에). 그래서 "플레이어" 규칙을 쓴다: x < 320이면 왼쪽 끝, 아니면 오른쪽 끝에 붙인다. 가상 좌표에서 106.67(= 320 × (4/3 − 1))만큼 옮기면 4:3 화면에서 가장자리까지의 거리가 그대로 유지된다.
- **고정은 호출 위치가 아니라 HUD 함수 단위로 한다** (그 함수 안의 모든 스프라이트 호출). 2P 쪽은 같은 함수의 다른 호출 위치에서 그리는데 1인 플레이 기록에는 나오지 않기 때문이다 (예: `DrawLifeHud`의 2P 분기는 x 416~584).
- 고정하는 함수: 게임플레이 HUD — 총알 `DrawAmmoHud` `0x4178A0`(1P x 24~60, 2P x 568~604), 생명 `DrawLifeHud` `0x417570`, 플레이어별 "PRESS START BUTTON"·크레디트 `0x406940`, `0x4068C0`(위치 표 `0x576600`: 1P (50, 412), 2P (392, 412)). 데모(타이틀 화면에서 도는 시연) HUD — 총알 `0x49A3F0`, 생명 `0x49A570`, "1P" `0x49A760`, 표시 `0x49A630`.
- 그대로 두는 것: 데모 화면 가운데의 큰 "PRESS START BUTTON"(`0x4067F0`), 데모 설명 그림(`0x49A7B0`), 자막(`0x436440`), 타이틀·전체 화면 그림(`0x460D30`, `0x495C80`, `0x495ED0`, `0x4998D0`), 여러 종류를 한 호출로 그리는 `0x41D000`("CANCEL WITH B BUTTON" 등), 조준점.
- **바로잡은 것 (사용자 발견):** 처음에는 `0x4067F0`을 플레이어 HUD로 분류해서 데모 화면 가운데 "PRESS START BUTTON"(x 160)이 왼쪽으로 밀렸다. 데모 화면 HUD도 게임플레이와 다른 함수라서 가장자리에 붙지 않았다. 데모 구간을 다시 추적해서 고쳤고, 6개 시점 촬영으로 가운데 문구가 화면 중앙선에 오고 데모 HUD가 왼쪽 끝에 붙는 것을 확인했다.
- 결과: 총알·1P 생명·"HOLD YOUR FIRE!"는 16:9 화면 왼쪽 끝, 2P "PRESS START BUTTON / CREDIT(S)"는 오른쪽 끝에 붙는다 (화면으로 확인). 점수, 보스 게이지, 이어하기 숫자 같은 HUD는 이번 실행에서 나오지 않아 분류하지 않았다.

- **한 일:** 사용자가 직접 실험(단계 2)을 해 보고 1챕터 시작 영상의 상하 띠가 넓어진 양옆을 덮지 못한다고 알려 줬다. 띠를 그리는 코드를 실행 추적으로 찾아(위 "영화 화면 띠") 실험 패치에서 띠 모델만 가로로 4/3배 넓혔다. 추적 기능(`[debug] trace_screen_quads`: 넓거나 화면 가장자리에 걸친 2D 사각형, 모든 모델의 행렬, 띠 모델의 호출 경로)과 영상 구간 촬영 스크립트 `tools/compat/intro-capture.ps1`을 만들었다.
- **결과:** 1챕터 시작 영상에서 띠가 16:9 화면 전체 폭을 덮는다. 함수 11개, 전역 변수 5개, 코드 위치 4개를 `re/`에 추가했다.
- **사용자 실행에서 겪은 문제:** 처음 사용자 실행에서는 dgVoodoo2 `ScalingMode`가 `stretched_ar`로 남아 있어서 좌우 검은 띠가 생기고 화면이 가로로 눌렸다. 실험은 `aspect_experiment`와 `ScalingMode = stretched`를 같이 바꿔야 한다. 정식 기능에서는 설정 하나로 둘 다 맞춰지게 해야 한다.
- **다음:** 다른 카메라 공간 물체 확인(G3-11), 조준 실험(G3-6).

### 2026-10-15 — 화면 비율 리버싱 (관련: G3-1~G3-5)

- **한 일:** 사용자가 정한 우선순위(리버싱 → 화면 비율 또는 주사율)에 따라 투영, 2D/HUD 그리기, 조준 변환을 분석했다. 전체 함수(2,881개)를 저장소 밖 임시 파일로 디컴파일해서 검색했다. 함수 28개, 전역 변수 8개, 코드 위치 4개를 `re/`에 기록했다. 실험용 패치 `[debug] aspect_experiment`와 촬영 스크립트 `tools/compat/aspect-capture.ps1`을 만들었다.
- **결과:** 위 "화면 비율 분석". 투영 비율 즉시값 2곳과 2D 그리기 호출 2곳만 바꿔서 16:9 화면의 3D와 2D 비율이 모두 맞는 것을 실행으로 확인했다. 조준과 가로 범위 판정은 위치만 찾았고 아직 실험하지 않았다.
- **실패한 시도와 주의:**
  - 처음에 D3D 장치 함수 표 오프셋을 16진수(`0x64`)로만 검색해서 `DrawPrimitive`를 못 찾았다. Ghidra는 100을 10진수로 쓴다.
  - Ghidra 헤드리스 스크립트 인자에 쉼표를 넣으면 `analyzeHeadless.bat`(cmd)가 인자를 나눈다.
- **다음:** 조준 실험(G3-6), 가시 범위 판정 확인(G3-7). 사용자에게 HUD 배치 방식과 아나모픽 방식 채택 여부를 묻는다.

### 2026-10-14 — 화면 처리 방식 결정 (화면 모드 분석에서 넘어온 내용)

- **결과:** 자체 렌더러를 만들기 전까지 창 모드, Alt+Enter, 고해상도는 dgVoodoo2(DX7 → D3D11 래퍼)로 처리하기로 했다 (사용자 결정, B안). 이 도메인의 "초기 호환성 확보용 기존 래퍼"가 확정된 것이다. 창 모드 직접 구현은 자체 렌더러의 요구 사항이 된다.
- **상세:** [platform-display.md](platform-display.md) "결정 사항"

### 2026-10-14 — 화면 모드 분석에서 넘어온 내용

- **결과:**
  - 렌더 구성: `SetDisplayMode(640, 480, 16bpp)`, primary 플립 체인(백버퍼 1장, `3DDEVICE`), 16비트 Z 버퍼 640×480, 16비트 텍스처 약 700개(일부 알파 포함). 매 프레임 `Flip(DDFLIP_WAIT)`.
  - Direct3D는 `IDirectDraw7::QueryInterface(IID_IDirect3D7)`로 얻는다 (호출 위치 `0x4BD2F3`).
  - Windows 호환 모드(`DWM8And16BitMitigation`, `apphelp.dll`)가 DirectDraw 함수 표를 덮어쓴다. DX7 수준에서 후킹하는 코드는 이것을 고려해야 한다.
- **상세:** [platform-display.md](platform-display.md) "화면 모드 분석 결과"

### 2026-10-14 — 호환성 조사에서 넘어온 내용

- **결과:**
  - Windows 11은 DX7을 `DDRAW.dll` → `D3DIM700.DLL` → `dxgi.dll` + 그래픽 드라이버 순서로 처리한다.
  - dgVoodoo2 v2.87.5(DX7 → D3D11 래퍼)를 게임 폴더에 넣으면 원본 수정 없이 **테두리 없는 창 + 1440×1080(4:3) 렌더링**이 가능하다. 3D와 HUD 모두 선명해진다. 1단계의 임시 렌더링 해결책으로 쓸 수 있다.
  - dgVoodoo2 기본 설정은 다중 모니터에서 보조 모니터를 전체 화면으로 잡는다. `AppControlledScreenMode=false`로 게임의 화면 모드 요청을 무시해야 창 모드가 된다.
- **상세:** [compat-survey.md](compat-survey.md) "dgVoodoo2 시험 결과"
