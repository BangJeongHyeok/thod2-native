# 플랫폼: 입력

- **상태:** 진행 중
- **관련 로드맵:** ROADMAP 1-3, 2-2
- **관련 코드:** `src/platform/` (`thod2/platform/input.h`, `input/input.cpp`), `src/core/patches/input_update.cpp`
- **마지막 갱신:** 2026-10-15

## 주요 목표

마우스, 게임패드, 라이트건 입력을 현대 API로 처리한다. 최종적으로 DirectInput 사용을 우리 입력 계층으로 교체하고, 현대 라이트건(Sinden, GUN4IR 등)과 2인 플레이를 지원할 수 있는 구조를 만든다.

**완료 기준:** 원본이 DirectInput을 직접 쓰지 않고, 마우스 조준이 어떤 해상도·화면 비율에서도 정확하며, 2인 입력 장치를 설정할 수 있다.

## 입력 갱신 분석 결과

2026-10-15. 근거는 Ghidra 디컴파일과 바이트 해석(`0x41E120`–`0x41E63B`, `0x41ED80`, `0x41EF50`, `0x41F430`, 점프 표 `0x41E63C`/`0x41E65C`). 함수와 전역 변수 목록은 `re/functions.csv`, `re/globals.csv`의 `doc = platform-input.md` 행.

### 흐름

1. **초기화** `InitInput`(`0x41DEC0`, `0x40AB40`에서 호출): 전역 변수를 지우고 `\\.\SEGAJOY.VXD`를 연다(현대 Windows에서는 실패). `LoadControllerIni`로 `Hod2.ini`를 읽고, `CreateInputDevices`로 DirectInput 7 키보드(버퍼 16)·마우스·조이스틱(최대 8개)을 만든 뒤 `ResolveControllerModes`로 플레이어별 장치 모드를 정한다. 실패하면 P1 모드 6, P2 모드 0.
2. **매 프레임** `UpdateInput`(`0x41E120`). 호출하는 곳은 `0x40E5F0`의 `call` 하나뿐이다. 조이스틱 → 마우스 → 키보드 배치 0 → 배치 1 순서로 장치 레코드를 채운 뒤, P1(슬롯 0)과 P2(슬롯 6)의 플레이어 레코드를 모드에 따라 만든다.
3. **사용하는 쪽:** `GetPlayerInputRecord`(`0x41E6D0`)가 플레이어 레코드를 넘기고, `TakeShotFlags`(`0x41E720`)가 사격·재장전 플래그를 소비하며, `GetShotPosition`(`0x41E6F0`)이 쏜 위치를 넘긴다 (호출하는 쪽은 미분석).

### `Hod2.ini` `[Controller]`와 장치 모드

`PLAYERn_INDEX`가 장치 종류를 고른다. `PLAYERn_DEVID`는 조이스틱일 때 열거된 장치 번호와 맞아야 한다.

| INDEX | 모드 | 동작 |
|---|---|---|
| 0 | 0 | 입력 없음 (플레이어 레코드의 슬롯 포인터만 설정) |
| 1 | 3 | 키보드 (P1은 배치 0, P2는 배치 1) |
| 2 | 6 | 마우스 + 키보드. 마우스 위치가 조준점 |
| 3–8 | 7–12 | 조이스틱 `INDEX-3`번. 제품 이름이 `MC PC LIGHT GUN`(`0x587D88`)이면 모드에 `0x80000000`을 붙여 총으로 다룬다 (`ReadGunJoystick`) |
| DEVID `0x104` | 13 / 14 | SEGAJOY.VXD 라이트건 (`ReadSegaGun`, `DeviceIoControl`) |

- 모드 2(이름 입력)와 5(마우스만)는 `ResolveControllerModes`가 만들지 않는다. 다른 곳에서 바꾸는 것으로 보인다 (G1-5).
- 테스트 사본의 `Hod2.ini`는 `PLAYER1_INDEX=2`, `PLAYER2_INDEX=1`이라 P1 모드 6, P2 모드 3이다.

### 버튼 비트

모든 레코드(0x34바이트, `ButtonRecord`)의 `held`(+0x08)에 쓰는 비트. `+0x0C`는 `~held`, `+0x10`은 이번 프레임에 눌린 비트, `+0x14`는 떼어진 비트다.

| 비트 | 뜻 | 키보드 배치 0 | 키보드 배치 1 | 마우스 | 조이스틱 버튼 (표 `0x587CDC`) |
|---|---|---|---|---|---|
| `0x80` | 오른쪽 | →, 숫자패드 6 | D | | 13, 스틱 X > 0x40 |
| `0x40` | 왼쪽 | ←, 숫자패드 4 | A | | 12, 스틱 X < -0x3F |
| `0x20` | 아래 | ↓, 숫자패드 2 | X | | 11, 스틱 Y > 0x40 |
| `0x10` | 위 | ↑, 숫자패드 8 | W | | 10, 스틱 Y < -0x3F |
| `0x08` | 시작 | Enter | 왼쪽 Shift | 가운데 버튼 | 8 |
| `0x04` | 사격 | Space | Tab (Alt를 누르고 있으면 무시) | 왼쪽 버튼 | 0 |
| `0x02` | 재장전 | 숫자패드 + | 왼쪽 Ctrl | 오른쪽 버튼 | 2 |
| `0x01` | ? | | | | 3 |

조이스틱 버튼 1, 4, 5, 6, 7, 9는 `0x400`, `0x200`, `0x100`, `0x20000`, `0x10000`, `0x800`이다 (뜻 미확인).

### 모드별 플레이어 레코드

| 모드 | type | 버튼 | 그 밖 |
|---|---|---|---|
| 3 | `1` (디지털), `+0x04 = 0xF06FE` | 키보드 레코드 복사 | |
| 6 | `0x80` (포인터) | 키보드 OR 마우스 (`not_held`도 OR) | 아래 마우스 처리 |
| 5 | `0x80` | 쓰지 않음 | 아래 마우스 처리 |
| 7–12 | 총이면 `0x80`, 아니면 `1` + `0xF06FE` | 조이스틱 OR 키보드 | |
| 13, 14 | `0x80` | `ReadSegaGun` 결과에 키보드 `held` OR | |
| 2 | `0x40` (이름 입력) | 쓰지 않음 | P1만 `g_inputNameEntry` 채움 |

마우스 처리: 마우스의 "눌린" 비트에서 사격(`0x04`)과 재장전(`0x02`) 플래그를 슬롯별로 세운다. 둘이 같은 프레임에 눌리면 재장전만 남긴다. 그다음 일회용 콜백(`g_inputCursorCallback`)이 없거나 1을 돌려주면 커서 위치(창 클라이언트 픽셀)를 `g_inputCursor[slot]`에 쓴다.

### 원본의 특이 동작 (재구현도 그대로 따름)

- **두 키보드 배치가 "이전 상태" 변수 하나(`0x7DB33C`)를 같이 쓴다.** 그래서 배치 1의 눌림·뗌은 같은 프레임 배치 0의 결과와 비교한 값이다. 2인 키보드 플레이에서 눌림 판정이 섞일 수 있다.
- **이름 입력 문자는 배치 1을 읽을 때 받은 키 이벤트만 남는다.** `ReadKeyboard`가 부를 때마다 이벤트 버퍼를 지우고 다시 읽는데, 배치 0을 읽을 때 이미 이벤트를 가져가기 때문이다. 실제 이름 입력이 이 경로를 쓰는지는 미확인(G1-5).
- 장치 읽기가 실패해서 다시 `Acquire`에 성공하면, 비어 있는(0) 상태로 버튼을 계산한다.

## 재구현과 검증

### 구조

- `src/platform/`(`thod2_platform_lib`): 게임 메모리 위치를 모르는 순수 구현. `InputMemory`(게임 전역 변수를 가리키는 포인터 묶음)와 `InputHost`(DirectInput·Win32·게임 함수 호출)를 받아서 동작한다. 그래서 테스트 버퍼로도, 게임 메모리로도, 원본 기록으로도 돌릴 수 있다.
- `src/core/patches/input_update.cpp`: 게임 주소로 `InputMemory`를 만들고, `0x40E5F0`의 `call 0x41E120`(`E8 2B FB 00 00`)을 우리 함수로 바꾼다 (`PatchBytes`로 원래 바이트를 확인한 뒤).
- 총 읽기 함수 두 개(`0x41F000`, `0x41F210`)는 장치가 없어 검증할 수 없어서 원본을 그대로 부른다.

### 비교 모드 (`[debug] input_compare = 1`)

매 프레임:

1. 입력 메모리(`0x7D98F8`–`0x7DB370`, `0x587D14`–`0x587D20`)를 저장한다.
2. **원본** `0x41E120`을 실행하면서 DirectInput 장치 함수 표(`Acquire`, `GetDeviceState`, `GetDeviceData`, `Poll`), 게임의 `GetCursorPos`·`ClientToScreen` 임포트, 일회용 커서 콜백 호출을 기록한다.
3. 저장한 상태로 되돌리고 **재구현**을 실행한다. 이때 장치·커서 호출은 실제로 하지 않고 2의 기록을 순서대로 돌려준다. 호출 순서·대상·크기가 다르면 "calls differ"로 센다.
4. 두 결과 메모리를 바이트 단위로 비교하고, 게임은 원본 결과로 계속한다 (비교 모드는 게임 동작을 바꾸지 않는다).
5. 600프레임마다 `thod2-native.log`에 요약을 쓴다. 다른 프레임은 처음 20개까지 주소와 바이트를 남긴다.

실행 도구: `tools/compat/input-compare-run.ps1` (테스트 사본의 ini에 `input_compare = 1`을 넣고 실행, 끝나면 ini를 되돌림). 기본은 `SendInput`(스캔 코드)으로 키보드·마우스 입력을 무작위로 넣는다. 게임 창이 맨 앞일 때만 보내고, 마우스는 게임 창 안으로만 움직이며, Alt+Tab은 보내지 않는다. `-Manual`이면 입력을 넣지 않고 사람이 플레이한다.

## 작업 기록

### 2026-10-15 — 입력 갱신 재구현과 원본 비교 (리버싱 파일럿, 관련: G1-1~G1-3, G2-1~G2-3)

- **한 일:** 입력 모듈을 Ghidra로 디컴파일하고 어셈블리로 세부를 확인했다. 함수 19개, 전역 변수 24개(+`g_diDevices` 갱신), 코드 위치 1개를 `re/`에 기록했다. `UpdateInput`, `ReadKeyboard`, `ReadMouse`, `ReadJoystick`, `GetCursorClientPos`, `ConsumeCursorCallback`을 재구현하고 비교 모드와 실행 스크립트를 만들었다. 단위 테스트 `platform_tests`(확인 28개)를 추가했다.
- **결과:**
  - 자동 입력 180초 실행: **10,800프레임 모두 원본과 일치**(메모리 불일치 0, 호출 순서 차이 0). 버튼이 눌린 프레임 3,714개. 관측된 비트: 마우스 `0xE`(사격, 재장전, 시작), 배치 0 `0xFE`, 배치 1 `0xFE`(`0x01`을 뺀 전부). 호출 75,599개, 커서 읽기 10,799회(커서 콜백이 0을 돌려준 프레임이 있어서 1회 적음, 이 경로도 일치).
  - **비교 장치 자체 확인(변이 시험):** 마우스 결과에 `0x200`을 일부러 더한 빌드에서는 600프레임 모두 불일치로 잡혔고, 바뀐 주소(`0x7DAAC9`, `0x7DAACD`, `0x7DAAD1`, `0x7DAE49`, `0x7DAE51`, `0x7DB341`)가 정확히 나왔다.
  - 재구현만 켠 실행(`reimplement_update = 1`, 20초): 정상 실행, 종료 확인창 뒤 종료 코드 0, `exception.log` 없음.
  - 테스트 사본 상태: P1 모드 6, P2 모드 3. 게임이 맨 앞이 아니면 매 프레임 장치 읽기가 실패하고 `Acquire`를 다시 부른다(프레임당 호출 10개). 맨 앞이면 7개.
  - **실패한 시도:** ① 처음 실행에서 게임 창이 포커스를 받지 못해 입력이 0회 들어갔다. `SwitchToThisWindow`로 해결했다. ② 64비트 PowerShell에서 `INPUT` 구조체의 공용체 위치를 4로 잡아 `SendInput`이 모두 실패했는데, 이것을 모른 채 첫 변이 시험(오른쪽 버튼에만 차이)을 "불일치 0"으로 봤다. 관측 비트 통계를 넣어서 발견했고, 구조체를 고친 뒤에는 실패 0이다. 그 실행에서 배치 1의 Tab(`0x04`)이 계속 눌린 것으로 보인 원인은 확인하지 못했다.
  - 주의: `-I`(격리 모드)로 Python을 돌리면 사용자 site-packages의 capstone을 못 찾는다. 스크립트 이름을 `dis.py`로 하면 표준 라이브러리 `dis`와 충돌한다.
- **다음:** 사용자가 `-Manual`로 실제 게임을 끝까지 플레이하며 비교한다(G2-4). 입력 결과를 쓰는 쪽(G1-4)을 찾는다. 파일럿 측정값은 [reverse-engineering.md](reverse-engineering.md) G3-4에 있다.

### 2026-10-15 — 파일 접근 분석에서 넘어온 내용

- **결과:** 게임이 시작할 때 `\\.\SEGAJOY.VXD`를 열려다 실패한다 (호출 위치 `0x41DF23`, 오류 2 = 파일 없음). 당시 세가 라이트건 드라이버(VxD, Windows 9x 방식)로 보인다. 현대 Windows에서는 쓸 수 없으므로, 라이트건은 DirectInput 장치나 마우스 입력으로 처리해야 한다.
- **상세:** [platform-filesystem.md](platform-filesystem.md) "파일 접근 분석 결과"

### 2026-10-14 — 호환성 조사에서 넘어온 내용

- **결과:** `Config.exe`(MFC 앱 `Hod2_Tool`)는 Player1/Player2 컨트롤러 선택, "MC PC Light Gun" 속성, 화면 밝기, 번쩍임 시간·색상을 설정해서 `Hod2.ini`에 저장한다. `Hod2.exe`와 `Config.exe` 둘 다 `DeviceIoControl`을 임포트한다 (당시 전용 라이트건 드라이버와 통신한 것으로 추정). 사용자 플레이 결과 마우스 조준은 정상이다.
