# 리버스 엔지니어링

- **상태:** 진행 중
- **관련 로드맵:** ROADMAP 2-1
- **관련 코드:** `re/`
- **마지막 갱신:** 2026-10-15

## 주요 목표

원본 게임의 동작(함수, 전역 변수, 구조체, 호출 관계)을 여러 사람이 공유할 수 있는 텍스트 형태로 기록한다. 다른 도메인이 함수를 재구현할 때 필요한 근거를 제공한다. 원본 코드를 포함하는 Ghidra 프로젝트 파일이나 디컴파일 코드는 커밋하지 않는다.

**완료 기준:** `re/functions.csv`와 Ghidra 적용 스크립트로 누구나 같은 분석 상태를 재현할 수 있고, 각 도메인이 필요로 하는 핵심 함수의 위치가 기록되어 있다.

## 리버싱 규모 산정

2026-10-15 측정. 다시 재려면 Ghidra GUI를 닫고 `.\tools\re\scope.ps1`을 실행한다 (약 1분, 본 프로젝트의 임시 사본에서 동작). 숫자는 테스트 사본의 `Hod2.exe`(SHA-256 `1D7126…CE69`) 기준이다.

### 측정 방법

1. 본 Ghidra 프로젝트(자동 분석 + `re/` 적용 상태)를 임시 폴더로 복사한다.
2. `ScopeCoverage.java`: `.text`가 함수로 얼마나 덮였는지, 다른 섹션에서 `.text`를 가리키는 포인터가 몇 개인지 센다.
3. `ScopeRecoverFunctions.java`: 포인터가 가리키는데 함수가 아닌 곳, 함수에 속하지 않은 명령 덩어리의 시작에 함수를 만든다 (최대 5회 반복).
4. 다시 `ScopeCoverage.java`, 그다음 `ScopeFuncStats.java`(함수별 크기, 명령 수, 호출자 수, 임포트·문자열 참조)와 `ScopeDecompStats.java`(모든 함수를 디컴파일해서 줄 수와 경고 수만 센다. 디컴파일 코드는 저장하지 않는다).
5. `tools/re/scope_summary.py`가 아래 코드 영역별로 합친다.

### 자동 분석이 놓친 함수

| | 함수 복구 전 | 복구 후 |
|---|---|---|
| 함수 수 (외부 함수 제외) | 1,876 | **2,881** |
| `.text` 중 함수 안 바이트 | 416,041 (52%) | 719,808 (91%) |
| 함수 밖 명령 바이트 | 263,122 | 1,211 |
| 정의 안 된 바이트 (패딩 `CC`/`90`/`00` 제외) | 68,142 | 35,506 |
| 데이터 → 코드 포인터 중 함수 시작이 아닌 대상 | 618곳 | 2곳 |

- `.text` 크기는 794,624 bytes. 데이터 섹션에서 `.text`를 가리키는 4바이트 값은 1,518개다.
- **Ghidra 자동 분석은 함수 포인터로만 불리는 함수를 대부분 놓친다.** 복구 단계에서 포인터 대상에 551개, 고아 명령 덩어리에 452개를 만들었다. 기존 기록의 `0x49E0C0`(대기 콜백)과 같은 경우다.
- 복구 뒤 자동 분석을 한 번 더 돌리면 2,938개가 된다 (측정 도구는 결과를 고정하려고 다시 돌리지 않는다).
- 남은 35,506 bytes(30바이트 이상 연속 81곳, 44,428 bytes)는 코드 안의 표나 아직 못 찾은 함수일 수 있다. 확인하지 않았다.

경계는 임포트·문자열 참조로 **추정**했다. VC6 링커는 목적 파일 순서대로 코드를 배치하므로 라이브러리가 뒤쪽에 모인다.

|---|---|---|---|---|---|---|---|---|---|---|
| 게임 | `0x401000`–`0x49D8B0` | `cam\%s`, `pol\%s`, `SS_SndLoadPack`, `HOD2 SAVE FILE`, 메뉴 문자열 | **1,990** | 579,778 | 158,074 | 10% | **986** | **93,733** | 720 | 17,616 |
| 엔진 플랫폼 (HGL) | `0x49D8B0`–`0x4A6380` | `HGLApp` 창 클래스, `hglCore.ini`, DirectSound 스트리밍, 프레임 대기, 세이브 | 144 | 31,372 | 9,448 | 1% | 35 | 6,402 | 38 | 192 |
| 엔진 수학·그래픽 (HGL) | `0x4A6380`–`0x4AB280` | 임포트 없음, 부동소수 비율 44%, 호출이 많은 작은 함수 (`0x4A8C60` 호출 446곳) | 79 | 19,507 | 6,090 | 44% | 1 | 3,046 | 18 | 115 |

- 함수 크기 분포 (전체): 16바이트 미만 257개, 16–64 717개, 64–256 1,083개, 256–1,024 705개, 1,024–4,096 119개, 4KB 이상 없음. 가장 큰 함수는 `0x4366C0`(3,972 bytes).
- **디컴파일 실패 0개.** 점프 표를 복구하지 못한 함수는 게임 영역 8개다 (복구 후 자동 분석을 다시 돌린 2,938개 기준 측정).
- "포인터 캐스트 줄"은 `(undefined`, `*(int *)(`, `*(float *)(`가 들어간 줄 수다. 구조체가 정해지지 않은 정도를 보여 준다.
- 게임 영역에서 `OutputDebugStringA`를 쓰는 함수가 있고, 일부는 자기 이름을 출력한다 (`SS_SndLoadPack`, `SS_EntryStageSE`, `SS_GetAudioVal` 등). 소스 파일 이름(`.c`, `.cpp`) 문자열은 없다.
- `.rdata`(724,992 bytes) 중 실수처럼 보이는 4바이트 값(절댓값 0.0001–100,000)이 54,167개, `.rdata`/`.data` 영역을 가리키는 포인터가 11,203개다. **게임 데이터 표가 실행 파일 안에 많이 들어 있다**는 뜻으로 본다 (내용은 미확인).
- 디버거 탐지 API(`IsDebuggerPresent`, `CheckRemoteDebuggerPresent`, `NtQueryInformationProcess`) 문자열이 없다.

### 가능성 판정

**기술적으로 가능하다.** 근거:

- 패킹·난독화·디버거 탐지가 없고, 재배치 정보 없이 고정 주소에 로드된다. 후킹과 함수 단위 교체에 유리하다.
- VC6 최적화 코드라 Ghidra 디컴파일이 전부 성공한다 (2,881/2,881).
- 리버싱이 필요 없는 라이브러리(CRT, D3DX, 예외 기록)가 668개 함수(23%)이고 영역이 뚜렷하게 나뉜다. 이 부분은 함수 단위로 분석하지 않고 통째로 대체한다.
- 하이브리드 기반(`dinput.dll` 프록시, IAT 후킹, `re/` CSV ↔ Ghidra 동기화, 실행 기록 도구)이 이미 있다.
- 공개된 선행 작업이 있다 (아래 "선행 작업"). 포맷 구조와 함수 역할을 찾을 때 실마리가 된다.

**어려운 점 (위험):**

1. **간접 호출이 많다.** 게임 함수 1,990개 중 986개는 직접 호출하는 곳이 없다 (함수 포인터 표로 불림). 적·이벤트·화면 상태를 표로 돌리는 태스크 구조로 추정한다. 이 표의 구조를 먼저 풀어야 호출 관계를 알 수 있다 (G3-6).
2. **구조체 복원이 핵심 비용이다.** 게임 영역 디컴파일 93,733줄 중 17,616줄이 원시 포인터 캐스트다. 공용 구조체(태스크, 적, 플레이어, 카메라, 모델)를 정해야 읽을 수 있는 코드가 된다.
3. **실행 검증 비용.** 교체한 함수가 원본과 같은지 보려면 게임을 실제로 돌려야 한다. 사용자 플레이 시간이 병목이 될 수 있다. 자동 비교(같은 입력으로 원본 함수와 재구현 함수를 둘 다 돌려 결과 비교) 도구가 필요하다.
4. **실행 파일 안의 데이터.** 독립 실행(M4) 단계에서는 `.rdata`의 데이터 표를 사용자의 `Hod2.exe`에서 읽어야 한다. 원본 데이터는 배포하지 않는다는 원칙과 충돌하지 않지만 추출기가 필요하다.
5. **실행 파일 빌드가 여러 개다.** 우리 것은 2001-03-22 링크(`.text` VirtualSize `0xC1940`)인데, 선행 작업은 2001-05-09 링크(`.text` `0xC2520`) 빌드를 분석했다. 주소가 다르다 (선행 작업 주소 6개 중 5개는 우리 실행 파일에서 함수 시작이 아님). 다른 빌드를 가진 사용자를 지원하려면 주소 대응 표가 필요하다.
6. **MinHook이 아직 없다.** 코드 후킹에 필요하고, 받기 전에 사용자 확인이 필요하다 (작업 규칙 6).

- AI 에이전트가 작업하면 읽기와 코드 작성은 빨라지지만, **실행 검증(게임 실행, 사용자 플레이)** 은 그대로 남는다. 마일스톤마다 처음부터 끝까지 플레이 확인이 필요하다.
- 위 속도는 숙련자 기준 **가정**이다. AI 에이전트 기준 실측과 보정은 아래 "파일럿 측정"에 있다.
- M1~M3만으로도 ROADMAP의 현대화 기능 대부분(고해상도, 입력, 오디오, 자산 덮어쓰기)이 가능하다. 게임 로직 전체 재구현(M4)은 장기 목표로 둔다.

**보정한 산정 (에이전트 작업 시간 기준):**

- 이 모듈은 쉬운 편이다: 직접 호출, 뚜렷한 전역 변수, 게임 로직과 분리됨. 게임 로직은 함수 포인터 표와 미정 구조체 때문에 함수당 3–5배 이상 걸린다고 본다.
- 함수당 (이름 + 재구현 + 검증): 쉬운 모듈 약 2.5분, 어려운 모듈 약 15분으로 잡는다.

| M4까지 전체 | 2,213 | 약 90–550시간 | 약 1,600만–8,000만 |

- 표본이 모듈 하나라서 범위가 넓다. 다음 서브시스템(타이밍 또는 오디오)을 끝낼 때마다 이 표를 다시 고친다.
- **에이전트 시간보다 먼저 막히는 것:** 사람이 하는 실제 플레이 검증(장면·모드마다), 장치가 필요한 경로(조이스틱, 라이트건), 사용자 확인이 필요한 결정. 이번 파일럿도 실제 플레이 검증(platform-input G2-4)은 남았다.
